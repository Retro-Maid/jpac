# GEO_EXPANSION_RESEARCH.md — 日本地理情報の統合リポジトリ化に向けた事前調査

jpac（jp-address-crosswalk）を起点に、日本の地理・国土に関するオープンデータを
「町字を軸に横断的に紐づけたリポジトリ」へ拡張できるか。その可否を、**先行事例**・
**接続可能性**・**ライセンス**の3点から調べた記録。

- 調査日: **2026-09-02**（各ライセンスの確認日は本文中に個別に記載）
- 対象読者: このリポジトリのスコープを決める人
- 機械可読版: [`config/candidate_sources.yml`](../config/candidate_sources.yml)
- 既存の規律: [`docs/POLICY.md`](POLICY.md) / [`docs/LICENSE_POLICY.md`](LICENSE_POLICY.md) /
  [`DATA_LICENSE.md`](../DATA_LICENSE.md)

> この文書は調査結果であり、決定ではない。実際に取り込む前に、各ソースの規約は
> `LICENSE_POLICY.md` §4 の手順（本文を逐語で読み、ハッシュを baseline として commit）で
> 再確認すること。以下のライセンス判定は、そのための下調べにすぎない。

## 0. 結論（先に3つ）

1. **「カタログ」は既にある。「クロスウォーク」は無い。** G空間情報センター、国土交通
   データプラットフォーム、data.go.jp は、いずれもデータを *探す* ための仕組みで、
   異なるデータの ID を *つなぐ* ための仕組みではない。jpac が持っている「恒久 ID +
   根拠 + confidence + 複数候補を潰さない」という性質は、既存のどの取り組みにも無い。
   ここが空いている。

2. **最大の技術的制約は、町字のポリゴンが手元に無いこと。** jpac が持つ座標は
   位置参照情報の **大字・町丁目の代表点** 1点だけで、これは `DATA_LICENSE.md` で
   「建物位置ではない」と明記した通りのものである。点は点であって面ではないので、
   **OSM の道路も、N02 の駅も、代表点だけでは町字に空間結合できない。**
   ここを解かない限り「jpacで紐づく」と言えるのは、キーで結合できるデータだけになる（§3）。

3. **最大のライセンス上の制約は2つ。OSM の ODbL と、国土数値情報のレイヤ別条件。**
   OSM を同じ DB に混ぜると、PDL 1.0 三者＋著作権不主張という現在のきれいな構成が
   share-alike に汚染されうる（§4）。国土数値情報は「全部 PDL 1.0」ではなく、
   **レイヤごとに条件が違い、非商用レイヤは再配布そのものが禁止**されている（§5）。
   ユーザーが最初に挙げた「OSM の道路」と「駅情報」は、まさにこの2つの地雷の上にある。

## 1. 先行事例 — 似た話は「ある」。ただし別の層にある

「日本地理情報総合リポジトリ」という発想は新しくない。ただし既存の取り組みは
**カタログ層**か**地物データ層**に集中していて、**ID 対応表層**はほぼ空いている。

### 1.1 カタログ層（データを探す）

| 取り組み | 運営 | 中身 | jpac との関係 |
|---|---|---|---|
| **G空間情報センター** | 一般社団法人 社会基盤情報流通推進協議会（AIGID） | 産官学の地理空間データの流通プラットフォーム。PLATEAU、法務省地図データ、国土数値情報のミラー等が集まる | **事実上の本命の先行事例**。ただし「データセットを登録・検索・配信する」場であり、約款も「利用条件は提供者ごとに設定される」と明言している。中身の ID を突き合わせる責任は利用者側に残る |
| **国土交通データプラットフォーム** | 国土交通省 | 省内外のデータを横断検索・可視化。2020年4月 Ver1.0、2023年4月 UI刷新 | 官製の統合窓口。API 提供はあるが、住所 ID を軸にした対応表としては公開されていない |
| **e-Govデータポータル / data.go.jp** | デジタル庁ほか | DCAT メタデータのカタログ | メタデータ層。jpac が既に踏んだ通り、**カタログのライセンス欄は当てにならない**（§7） |
| **awesome-japan-opendata** | コミュニティ | 日本のオープンデータのリンク集 | 人力リンク集。機械可読ではない |

### 1.2 地物データ層（地物そのものを配る）

| 取り組み | 中身 | ライセンス | jpac との関係 |
|---|---|---|---|
| **Geoshape リポジトリ**（ROIS-DS 人文学オープンデータ共同利用センター / CODH） | 国勢調査町丁・字等別境界データセット（2020年版で町丁・字等 **220,814件**）、歴史的行政区域データセット | **CC BY 4.0**（e-Stat 利用規約の遵守が条件）。クレジット例「『国勢調査町丁・字等別境界データセット』（CODH作成）」 | **小地域ポリゴンを第三者が再配布している実例**。§3 の突破口候補。ただし ID は e-Stat の `KEY_CODE` 系であって町字IDではない |
| **Linked Open Addresses Japan**（uedayou） | 国土数値情報・位置参照情報・e-Stat を統合し、行政区画ポリゴン付き住所を RDF/LOD で提供。鉄道駅LOD、Wikidata 等と接続 | **CC BY-SA 4.0** | **発想が最も近い先行事例**。「複数の公的データを住所を軸に統合し、周辺データと接続する」という狙いは同じ。相違点は (a) 恒久IDと根拠・confidence を持たない、(b) ABR 町字IDではなく `131010011000` 形式の住所コードを軸にする、(c) share-alike ライセンス |
| **geolonia/japanese-addresses** / **-v2** | 全国の町丁目レベル住所データと住所正規化ライブラリ。v2 は町字・住居表示・地番まで | オープン（採用時に要確認） | 住所の *正規化* が主眼。対応関係の根拠は保持しない |
| **公益財団法人 国土地理協会** 全国町丁目・字界地図データベース | 約18万件の町丁目・字界ポリゴンと代表点、11桁住所コード | **有償・商用** | オープンデータではない。ここを避けられることが本プロジェクトの意義でもある |
| **Overture Maps Foundation** | グローバルな地物 DB。GERS という恒久 ID 体系を持つ | CDLA-Permissive 2.0。ただし **transportation テーマは OSM 由来のため ODbL** | 「恒久IDで地物を横串にする」という発想の世界版。日本の行政 ID とは接続していない |

### 1.3 政府自身が同じことをやっている層

見落とせないのは、**デジタル庁のベース・レジストリ計画そのものが、この構想の上位互換**である点。

- ABR（アドレス・ベース・レジストリ）はその一部にすぎない。
- **法人ベース・レジストリ**は 2026年3月に提供開始（商業登記情報の一元管理）。
- **不動産ベース・レジストリ**（不動産登記情報）も整備予定。
- 整備順は「法人 → 住所 → 不動産登記」と説明されている。

つまり「法人」「不動産」については、数年内に公式のレジストリが出てくる可能性が高い。
**その領域を自作しにいくのは筋が悪い。** jpac が価値を出せるのは、
「政府が別々に整備したレジストリ同士を、根拠付きで突き合わせる」ところであって、
レジストリそのものを作るところではない。

### 1.4 まとめ：jpac の立ち位置

> カタログは AIGID と国交省がやっている。地物データは各省庁が配っている。
> レジストリはデジタル庁が作っている。**誰もやっていないのは、それらの ID を
> 「どちらの方向からでも辿れる形」で、根拠と信頼度つきで対応づけることだけ。**

拡張の方向は「データを増やす」ではなく「**対応表を増やす**」であるべき。
これは既存の `docs/POLICY.md` §1 の言い方（crosswalk database）とも整合する。

## 2. 評価の軸：「何のキーで町字に届くか」

発行機関別に並べても意味がない。重要なのは**接続方式**なので、候補は次の5つに分類する。

| 区分 | 接続方法 | 難易度 | 該当する代表例 |
|---|---|---|---|
| **(a)** | 市区町村コード（JIS 5桁 / LG 6桁） | 容易。ただし粒度が市区町村止まり | 統計表の大半、N03 行政区域、気象観測所 |
| **(b)** | ABR 町字ID | **唯一きれいに繋がる**。該当データは極めて少ない | ABR 自身の各マスター、ABR 町字・郵便番号変換表 |
| **(c)** | 郵便番号 | jpac が既に橋を架けているので、ほぼ無料で繋がる | 郵便番号キーの各種民間・自治体データ |
| **(d)** | 幾何情報のみ（点・線・面。行政キーを持たない） | **町字ポリゴンが無いと繋がらない（§3）** | **OSM の道路、N02 の駅**、国土数値情報のほぼ全レイヤ、PLATEAU |
| **(e)** | 住所文字列 | ジオコーディングが必要。曖昧性が発生する | 自治体の施設一覧、民間 POI |

ユーザーが例に挙げた「OSM の道路」も「国交省の駅情報」も、**どちらも (d)** である。
つまりこの構想の成否は、ほぼ §3 に集約される。

なお **(e) は原則として採らない**。住所文字列からの推定は、jpac が `*_status` /
`*_confidence` 列でわざわざ排除してきた種類の曖昧さを、データの中心に持ち込むことになる。
やるとしても「対応表」ではなく「参考情報」として、別レイヤに隔離すべき。

## 3. 決定的な制約 1 — 町字のポリゴンが実質的に存在しない

### 3.1 何が問題か

jpac が持つ座標は、位置参照情報（大字・町丁目レベル）の**代表点**である。
`DATA_LICENSE.md` は「建物位置ではなく大字・町丁目全体の代表点である」と明示することを
国交省の条件として受け入れている。代表点は point-in-polygon の材料にならない。

したがって、駅（点）や道路（線）を町字に割り当てるには、**町字の境界ポリゴン**が要る。
候補を当たった結果は次の通り。

### 3.2 町字ポリゴンの候補と判定

| 候補 | 発行 | 粒度 | ライセンス | 再配布 | 判定 |
|---|---|---|---|---|---|
| **国勢調査 小地域（町丁・字等別）境界データ** | 総務省統計局 / e-Stat | 町丁・字等（約22万件） | e-Stat 利用規約＝**政府標準利用規約（第2.0版）**準拠、CC BY 互換。統計地理情報システム機能利用規約 第6条が「コンテンツの利用条件等は e-Stat 利用規約に準ずる」と明記 | **可**（出典表示・加工明示） | ⭕ **最有力。ただしキーが `KEY_CODE`（JIS市区町村コード＋小地域コード）で、町字IDではない** |
| 同上の CODH 版（Geoshape） | ROIS-DS CODH | 同上 | **CC BY 4.0** | 可（クレジット必須、e-Stat 規約遵守が条件） | ⭕ 第三者による再配布の実例として重要。ただし CODH の加工が入る |
| **基盤地図情報（基本項目）** の `CommBdry`（町字界線）/ `CommPt`（町字代表点） | 国土地理院 | 町字 | **基本測量成果**。測量法第29条（複製）/第30条（使用）の承認体系下 | **要承認** | ❌ **実質ブロック**（§3.3） |
| **登記所備付地図データ** | 法務省（G空間情報センター経由） | 筆（地番） | 登記所備付地図データ利用規約（一部を除き**政府標準利用規約（第2.0版）**準拠） | **可** | 🔶 **ボトムアップで町字面を組める可能性**（§6.5） |
| **国土数値情報 N03 行政区域** | 国土交通省 | **市区町村まで** | CC BY 4.0 | 可 | ⚠️ 町字には届かない。(a) 用途 |
| 全国町丁目・字界地図データベース | 国土地理協会 | 町字（約18万件） | **有償** | — | ❌ オープンデータではない |
| **ABR 町字マスター位置参照拡張** の `plygn_*` 列 | デジタル庁 | 町字 | PDL 1.0 | 可 | ❌ **実測で全国 0 件**（§3.4.2）。ポリゴンの外部ファイル参照の器はあるが、参照先ファイル名が全行空 |
| **標準地域メッシュ（JIS X 0410）** | — | メッシュ | 規格。データは各所 | 可 | 🔶 ポリゴン問題を回避する退避策。ただし「町字」ではなくなる |

### 3.3 基盤地図情報が使えない理由（ここは間違えやすい）

国土地理院の Q&A（`https://www.gsi.go.jp/LAW/2930-qa.html`）は、承認申請が必要な例として
**「誰でも見られるブログ等、不特定多数への公開」**、**「独自データを大量に付加した場合」**、
**「標高データから段彩図を作成する等の加工成果物（第30条 使用承認）」** を挙げている。
申請不要とされるのは、地理院タイルのリアルタイム読込表示、書籍への挿入、組織内利用
（そのまま複製は30部まで）、論文・学会発表といった範囲である。

**再配布可能なデータセットを公開する**という本プロジェクトの形は、この「申請不要」の
どれにも当てはまらない。

> ⚠️ **論理の混同に注意。** `DATA_LICENSE.md` は、位置参照情報が測量法の承認体系を
> 免れる理由を「国土数値情報規約 §1.2（個別法令）に含まれないから」と説明している。
> **この論理は国土地理院の産品には適用できない。** GSI 産品は国土交通省サイトの
> 利用規約ではなく、測量法が直接掛かる。ここを取り違えると、このリポジトリで
> 唯一きれいに整理できている部分が壊れる。

### 3.4 残る本丸：`KEY_CODE` ↔ 町字ID の公式対応表は「設計され、空のまま公開されている」

初回調査では「公式の対応表は見当たらない」とだけ書いた。これは不正確だった。
**対応表は設計され、列も存在し、実際に配布されている。中身が全国で空なだけである。**
以下は 2026-09-02 に実データを取得して数えた結果で、
再取得は [`tools/probe_abr_town_pos.py`](../tools/probe_abr_town_pos.py) で行える。

#### 3.4.1 位置参照拡張は、発行者自身が「ID対応表」と呼んでいる

ABR の **町字マスター位置参照拡張**（`mt_town_pos_pref{01..47}.csv`）は、
デジタル庁の解説によれば、町字ID から国交省 位置参照情報および
総務省統計局 国勢調査小地域境界データへリンクするための **ID対応表**である。
そして実際に配布されている CSV のヘッダは、まさにその通りの列を持つ（実測、全47県で同一）：

```
lg_code, machiaza_id, rsdt_addr_flg,
rep_lon, rep_lat, rep_srid, rep_scale, rep_src_code,
plygn_fname, plygn_kcode, plygn_fmt, plygn_srid, plygn_scale, plygn_src_code,
pos_oaza_cho_chome_code, pos_data_mnt_year,
cns_bnd_s_area_kcode, cns_bnd_year
```

`cns_bnd_s_area_kcode` が国勢調査 小地域（町丁・字等別）の KEY_CODE、
`cns_bnd_year` がその整備年度である。**つまり「構想」ではなく「公開スキーマ」である。**
2021年の政府CIO補佐官等ディスカッションペーパーを持ち出すまでもない
（同ペーパー自身が政府の公式見解ではない旨を明記しているので、根拠としても弱い）。
根拠は配布物のヘッダそのもので足りる。

#### 3.4.2 実測：全国 337,641 行、国勢調査列の非空は 0 件

| 列 | 非空件数 | 割合 |
|---|---:|---:|
| `rep_lon` / `rep_lat`（代表点） | 337,641 | 100.00% |
| `pos_oaza_cho_chome_code`（国交省 大字町丁目コード） | **208,501** | **61.75%** |
| `pos_data_mnt_year` | 208,501 | 61.75% |
| **`cns_bnd_s_area_kcode`（国勢調査 KEY_CODE）** | **0** | **0.00%** |
| **`cns_bnd_year`** | **0** | **0.00%** |
| `plygn_fname` / `plygn_kcode` / `plygn_fmt` / `plygn_srid` / `plygn_scale` | **0** | **0.00%** |

47都道府県すべてで `cns_bnd_s_area_kcode` は 0 件。一部地域だけ埋まっている、
という状態ですらない。

**ここで重要なのは対照列である。** 同じ「リンク用ブロック」にある国交省側の
`pos_oaza_cho_chome_code` は **61.75% 埋まっている**。したがって今回の所見は
「位置参照拡張のリンク機構が丸ごと空だった」ではなく、
**「国交省側のリンクは実装されて配布され、国勢調査側のリンクだけが空のまま配布されている」**
という、より限定的で、より確度の高い主張になる。

なお `plygn_src_code` だけは全行に値があるが、値は全行 `0` で、
参照先ファイル名（`plygn_fname`）は空。**ポリゴンも「枠だけあって中身が無い」状態**である。

#### 3.4.3 さらに悪い所見：位置参照拡張は町字マスターにも十分には繋がらない

対応表として使うなら、まず自分の親マスターに繋がっていなければならない。
`(lg_code, machiaza_id)` で `mt_town_all.csv`（726,170 町字）に突き合わせた結果：

| 指標 | 実測 |
|---|---:|
| 位置参照拡張の行数 | 337,641 |
| うち町字マスターに一致する行 | 209,332（**62.0%**） |
| 町字マスター 726,170 件のうち、位置参照拡張のレコードを持つもの | 196,162（**27.0%**） |
| 位置参照拡張に登場する市区町村 | 1,894 |
| うち全行が一致する市区町村 | 396 |
| うち一部のみ一致 | 1,430 |
| うち**1行も一致しない**市区町村 | **68** |

不一致は取り違えではなく、**採番系列そのものが食い違っている**市区町村がある。例：

```
札幌市北区 (lg_code=011061)
  町字マスター    machiaza_id = 0001000, 0002001, 0002002, ...
  位置参照拡張    machiaza_id = 0000101, 0000102, 0000103, ...   ← 一致しない
```

都市部は良好（千代田区 140/140→136 一致、新宿区 175→174 一致）で、
郊外・町村部で崩れる（八丈町 26→14）。配布物が古いわけでもない：
DCAT の `modified` は **2025-10-27**（東京都版）である。

#### 3.4.4 結論

> **ABR 町字ID ↔ 国勢調査 KEY_CODE の公式対応表は、「無い」のではなく
> 「列として設計され、全国 0 件のまま配布されている」。**
> したがって jpac が使える公式クロスウォークは存在しない。
> ただしこれは「政府が考えていなかった」ことの証拠ではなく、
> **政府が同じ必要を認識し、器を用意し、まだ埋めていない**ことの証拠である。

そして位置参照拡張は、代替の座標源としても弱い（町字の 27.0% しか覆わない）。
jpac が既に持っている位置参照情報由来の代表点のほうが広い。

見方を変えれば、これは**最も価値のある拡張テーマ**でもある。
「小地域コード ↔ 町字ID」の根拠付き対応表は誰も公開しておらず、
これがあれば e-Stat の全小地域統計（人口・世帯・産業）が一挙に町字に繋がる。
政府が空のままにしている器を、根拠付きで埋めるのが jpac の仕事になる。

### 3.5 §3 の結論

- 代表点をポリゴンの代わりに使うことは**しない**。`DATA_LICENSE.md` の約束に反する。
- 基盤地図情報は測量法の承認体系にあるため、**再配布を前提とする本プロジェクトには入れない**
  （`LIMITATIONS.md` が既に GSI 住居表示住所を除外しているのと同じ理由が、より強く効く）。
- したがって **次期スコープは (a)(b)(c) に限定**し、(d) の幾何レイヤは
  「別リポジトリ・空間結合済みの兄弟成果物」として切り離すのが正直な設計。
- **その次の中核テーマを「小地域 ↔ 町字クロスウォーク」に置く**。これが解ければ (d) が開く。

## 4. 決定的な制約 2 — OSM（ODbL）は現在のライセンス構成を壊す

### 4.1 何が起きるか

現在の jpac の4ソースは、PDL 1.0 ×3 ＋ 日本郵便（著作権不主張）で、**すべて表示のみ**。
share-alike は1つも無い。

OSM は **ODbL 1.0**。ODbL は *Derived Database* に share-alike を課す。
OSM データを同一 DB に統合すると、**統合後のデータベース全体を ODbL で提供する義務**が
生じうる。これは、このリポジトリが最も慎重に組み立ててきた部分を根本から変える。

### 4.2 回避策（OSM 財団自身が示している）

| 手法 | 内容 | 評価 |
|---|---|---|
| **Collective Database** | OSM データが「独立したデータベースの集合体」の一部である場合、share-alike は掛からない。OSMF の Collective Database Guideline は、**同一の地域断面において、あるデータ種別が全部 OSM か全部非 OSM のどちらかであれば独立とみなす**と例示している | 🔶 有効だが、「町字IDに OSM の要素IDを対応づける表」はまさに混ぜる行為であり、独立性の主張は苦しい |
| **Produced Work** | 地図画像や集計結果など「成果物」として出す。成果物には任意の条件を付けられるが、請求に応じて元データまたは Derived Database を ODbL で提供する義務が残る | 🔶 タイル配信等には使えるが、対応表の配布には向かない |
| **物理的に分離** | OSM 由来の対応表だけを別リポジトリ・ODbL で出す | ⭕ **推奨。** jpac 本体のライセンス構成を保てる |
| **使わない** | 国土数値情報で代替する | ⭕ ユーザーが挙げた用途はほぼ代替可能（§5） |

### 4.3 Overture Maps も同じ問題を持ち込む

Overture は原則 **CDLA-Permissive 2.0** だが、**transportation テーマ（道路・鉄道・
フェリー航路・公共交通）は OSM 由来のため ODbL** で提供される。したがって
「Overture を使えば OSM の share-alike を回避できる」は**成り立たない**。
places テーマ等は CDLA なので別扱いになる。

### 4.4 §4 の結論

**OSM は jpac 本体に入れない。** 入れるなら独立リポジトリで、ODbL 明示のうえ。
ユーザーが例示した「OSM の道路」については、次節の N13（道路）が **CC BY 4.0** で
提供されており、行政データとの整合性という点でもそちらが筋が良い。

## 7. 許諾・確認の運用 — jpac の既存規律をそのまま拡張する

このリポジトリは既に、かなり厳しいライセンス規律を持っている。
拡張にあたっては、それを緩めるのではなく**そのまま適用範囲を広げる**のが正解。

1. **カタログのライセンス欄を信用しない。**
   `sources.yml` の ABR エントリには、DCAT フィードが CC BY 4.0 を広告している一方で
   規約ページは PDL 1.0 と書いている、という不一致が記録されている。これは
   「カタログ由来のライセンス情報は証拠にならない」という自前の実証例である。
   G空間情報センターの約款自身も「利用条件は提供者ごとに設定される」と述べている。
   **発行者自身の規約ページを逐語で読み、確認日とハッシュを記録すること。**

2. **国土数値情報は 1 レイヤ = 1 ソースとして扱う。**
   「MLIT のライセンス」という単位は存在しない。`sources.yml` の構造で言えば、
   レイヤごとに `license` ブロックを持たせる必要がある。

3. **`text_sha256` baseline は新規ソースにも必須。** `LICENSE_POLICY.md` §4 の
   「trust-on-first-use なし」を緩めない。ソースが増えるほど、ここが効く。

4. **share-alike ソースは物理的に分離する。** ODbL / CC BY-SA を、
   表示のみのソースと同じ成果物に混ぜない。混ぜた瞬間に `DATA_LICENSE.md` の
   「4者の条件をそれぞれ流す」という設計が破綻する。

5. **裁量条項・登録要件のあるソース（法務省、ODPT）は、その条件を下流へ明示的に伝える。**

6. **政府標準利用規約（第2.0版）と PDL 1.0 は別物として記録する。** 現行4ソースは
   PDL 側だが、e-Stat・法務省・産総研は政府標準側。`DATA_LICENSE.md` が
   「4者の異なる条件を1つに丸めない」としているのと同じ理由で、ここも丸めない。

## 8. 推奨スコープと段階計画

### 次期（v2） — キー結合のみ。ポリゴンには手を出さない

- 追加ソース：総務省 全国地方公共団体コード
- **ABR 町字マスター位置参照拡張は §3.4 の実測を受けて格下げ。** 採用する場合も
  「座標源」ではなく「国交省 大字町丁目コードとの第2の対応（61.75%、親マスター一致
  62.0%）」として、既存の `mlit_*` 系統の裏取りに使う。既存の代表点を置き換えない
- 目的：既存 crosswalk の粒度と根拠を厚くする。設計の変更は無い
- リスク：低い

### その次（v3） — **小地域 ↔ 町字クロスウォーク**（最重要）

政府が器を用意して空のままにしている場所（§3.4.4）を、jpac の作法で埋める。

- 追加ソース：e-Stat 国勢調査 小地域境界＋小地域集計
- 成果：`KEY_CODE` ↔ `machiaza_id` の対応表。既存と同様に
  `relation_type` / `confidence` / `candidate_count` / `status` を持たせる
- これが解けると：**全国勢調査小地域統計が町字に繋がる**、そして
  **町字ポリゴンが手に入るので (d) の幾何レイヤが開く**
- リスク：高い。V1 本体と同規模の照合問題。名称一致に頼らない設計が要る

**設計上、最初から織り込むべきこと（3つ）**

1. **国勢調査年をキーの一部にする。** 小地域は国勢調査のたびに引き直される。
   `(machiaza_id, key_code)` ではなく `(machiaza_id, key_code, census_year)` を
   対応の単位にすること。年をメタデータ列に落とすと、2020年版と2025年版の
   引き直しが黙って混ざる。ABR 側の器も `cns_bnd_year` を別列として持っている
   （空だが）ので、設計意図としても年別で正しい。
2. **1:1 を前提にしない。** 小地域は国勢調査の調査区由来で、町字とは別体系。
   1:N・N:1・部分重複が常態。V1 で 591件の住所が複数行に展開されたのと同じ扱いを、
   最初から前提にする。
3. **ABR の `cns_bnd_s_area_kcode` 列を監視対象にする。** 現在 0 件だが、
   将来 1 件でも埋まれば、それは `relation_type = official` の**正解データ**になる。
   自前の照合器を検証するラベル付きの答え合わせ集合であって、
   カバレッジそのものより価値が高い。`tools/probe_abr_town_pos.py` を
   定期的に回して非空件数を見ておくこと。

### その先（v4） — 幾何レイヤ（別リポジトリ）

- 追加ソース：N02 鉄道、N13 道路、N07/P11 バス、S12 駅別乗降客数、P29/P04 施設、
  PLATEAU（都市部）
- 前提：v3 の町字ポリゴン
- **OSM は入れない。** どうしても必要なら ODbL 明示の第3のリポジトリで

### 入れないと決めるもの

| 対象 | 理由 |
|---|---|

## 10. N02（鉄道）を紐づける — 設計案

- 調査日: **2026-09-05**（§1〜§9 は 2026-09-02）
- 対象: 国土数値情報 **N02 鉄道**（路線・駅）

§8 の段階計画は N02 を「v4・別リポジトリ・町字ポリゴンが前提」に置いた。
**この置き方は、粒度を1つに固定していた点で厳しすぎる。** 町字では繋がらないが、
**市区町村では確定的に繋がる**。以下はその切り分けである。

### 10.1 まず版の選択 — v2.3 ではなく 2025年版を使う

| | v2.3（`KsjTmplt-N02-v2_3.html`） | **2025年版**（`KsjTmplt-N02-2025.html`） |
|---|---|---|
| 対応年度 | 2015〜2020年度（平成27〜令和2） | 基準日 **2025-12-31** |
| 駅の属性 | N02_001〜005（駅名まで） | + **N02_005c 駅コード** / **N02_005g 駅グループコード** |
| 一覧ページの利用許諾条件欄 | — | **`CC_BY_4.0`** |
| 詳細ページの逐語 | 「令和2年度：適用する利用規約に基づく（オープンデータ）／それ以前：商用可」 | 「2020年（令和2年）以降：オープンデータ（CC_BY_4.0）／上記以外：商用可」 |

**駅コードの有無が決定的**である。§10.4 の重複排除も、S12 との接続も、
**駅コード／グループコードが無いと成立しない**。v2.3 にはこの列が無い。

**ライセンスの年度割れは、版の選択では解けない**点に注意。同じファイル群の中で
**2020年度以降のスライスだけが新規約（PDL 1.0）側**、それ以前は**旧約款の「商用可」**である。
§5.2 の逐語では「商用可」も*複製物の再配布を含む*ので再配布自体は可能だが、**条件は別物**である。
`DATA_LICENSE.md` の「4者の異なる条件を1つに丸めない」をそのまま適用し、
**取り込むのは 2020年度以降のスライスに限る**のが安全側。年度混在のまま
「N02 は CC BY」と書くのは、この文書が §5.3 で否定した丸め方そのものになる。

この年度割れは **v2.3 と 2025年版のどちらにも同じように掛かる**（両方の詳細ページが同じ
表記を持つ）ので、2025年版を選んでも消えない。逆に **v2.3 が使えないわけでもない**：
v2.3 の最終年度（令和2年度＝2020年度）は新規約側にいる。
**v2.3 を退ける理由はライセンスではなく、駅コードが無いことである。**

### 10.2 決定的な事実 — N02 に行政コードは無い

路線・駅とも属性は N02_001 鉄道区分 / N02_002 事業者種別 / N02_003 路線名 /
N02_004 運営会社（＋駅は N02_005 駅名, 005c 駅コード, 005g グループコード）だけで、
**市区町村コードも住所も持たない**（2026-09-05、両版の詳細ページで確認）。

> **したがって N02 には「キーだけで繋がる道」が存在しない。** §2 の分類 (d) のままである。
> 繋げるなら空間結合か、名寄せのどちらかしかない。

さらに **駅は点ではなく線**である（「鉄道路線の一部分として整備」）。
測地系は路線・駅とも **JGD2011 /（B, L）**。

### 10.3 提案：粒度で2層に割る

#### Tier A — 駅・路線 → **市区町村**（確定。今すぐできる）

**N03 行政区域**は市区町村ポリゴンで、素の CC BY 4.0（§5.4 で ⭕ 判定済）。
N02 の線を N03 のポリゴンに空間結合すれば、**駅 → `lg_code`** が得られる。

- ポリゴン問題は**町字レベルにしか存在しない**。市区町村ポリゴンは公開されている
- 出力される対応は `lg_code` を持つ。jpac が既にキーにしている列である
- **入力は (d) だが、出力は (a) になる。** この再分類が §8 で抜けていた。
  N02 の一部は v4 を待たずに前倒しできる
- `relation_type = spatial_containment` / `status = auto` を与えてよい唯一の層

```
N02 駅（線, JGD2011）  --空間結合-->  N03 市区町村ポリゴン  -->  lg_code
                                                              -->  jpac の既存3系統
                                                                   （郵便番号・国交省コード・市外局番）
```

これだけで「**この市区町村にある駅の一覧**」「**この路線が通る市区町村**」
「**市外局番の番号区画に含まれる駅**」が、推定を一切挟まずに引ける。

#### Tier B — 駅 → **町字**（候補のみ。既定では出さない）

代表点への最近傍で k 件の候補＋距離を持たせる案。**推奨はするが、条件付きで。**

1. §3.5 は「代表点をポリゴンの代わりに使うことは**しない**」と決めている。
   最近傍は point-in-polygon ではないので禁止事項そのものではないが、
   **下流は必ず「その町字にある」と読む**。読み違えを構造的に不可能にするため、
   `relation_type` は `spatial_containment` と共用せず、
   **`nearest_rep_point` のような別の名前**にすること。`status = auto` は与えない
2. §5.2 が記録した通り、国土数値情報の**空間誤差は数百メートル程度**。
   新宿区や中央区では**町字のほうが誤差より小さい**。
   つまり Tier B は、**需要が最も高い都心部でこそ誤差以下**になり、
   町字が大きい郡部でしか信用できない。需要と精度が逆を向いている
3. 結論：**参考情報／診断出力として別ファイルに隔離**するか、
   データが支えられる距離しきい値で足切りする。本体の対応表には入れない。
   Tier A の成果に相乗りさせないこと

### 10.4 実装上の落とし穴

| 論点 | 内容 |
|---|---|
| **駅は1駅1フィーチャではない** | ホーム・線路ごとに複数の線分に分かれる。**N02_005g グループコードで束ねてから**結合しないと行数が水増しされる。同一駅名でも別会社なら別グループ |
| **1:N は正しい出力** | 駅も路線も市区町村界を跨ぐ。V1 で 591件の住所が複数行になったのと同じ扱いを最初から前提にする。`candidate_count` を持たせる |
| **測地系** | N02・N03 とも JGD2011。jpac の代表点（位置参照情報由来）の測地系と一致するかを結合前に確認する。黙って混ぜるのがこの種の作業の典型的な失敗 |
| **廃線・未成線** | 2025年版に廃止区間が含まれるかを**未確認**。含まれるなら有効性フィルタが要る。時系列は N05 の担当だが、**N05 の利用許諾条件は `非商用`＝再配布不可**（一覧ページ、2026-09-05 確認。§5.2 の逐語の通り非商用は複製物の再配布を許諾していない）。§5.4 の棚卸しでも N05 は 🔶 側に置かれており、今回の確認はそれを裏付けるもの |
| **ライセンスの逐語確認** | §5.4 の表を根拠に使わない。取り込み時に N02 の詳細ページの利用許諾条件を逐語で読み、`LICENSE_POLICY.md` §4 の手順でハッシュを記録する |

### 10.5 N02 の周辺で繋がるもの／繋がらないもの

| 相手 | 経路 | 判定 |
|---|---|---|
| **S12 駅別乗降客数** | S12_001c 駅コード／S12_001g グループコードでのキー結合。**オープンデータ（CC_BY_4.0）**、2011〜2024年度、線形、JGD2011（2024年版の詳細ページ、2026-09-05 確認） | 🔶 **採番系が N02 と同一かは未確認。** 詳細ページは N02 との関係を明記していない（S12_001g の定義は「300m以内の同名駅をグループ化」）。実データで突合してから ⭕ にすること。いずれにせよ N02 系内部の接続であって、住所に繋げるものではない |
| N05 鉄道時系列 | 駅コード系 | ❌ **非商用＝再配布不可** |
| 駅名 ↔ 町字名（「新宿三丁目駅」↔ 町字「新宿三丁目」） | 文字列一致 | 🔶 **Tier B の confidence を上げる補助信号としてのみ**。主たる関係にはしない。§2 が (e) を排除した線を越えないこと |
| 事業者名 ↔ 法人ベース・レジストリ | N02_004 運営会社の文字列 | 🔶 将来。法人側の整備待ち（§6.1） |

### 10.6 §8 への差分

v4 に置いた N02 のうち、**Tier A（駅・路線 → 市区町村）は v2 相当に前倒しできる**。
町字ポリゴン（v3）を待つ必要があるのは Tier B だけである。
ただし Tier A の成果物は「市区町村レベルの対応」であって、
**jpac の売りである町字粒度ではない**。別テーブルとして分けて出すのが正直な設計。
