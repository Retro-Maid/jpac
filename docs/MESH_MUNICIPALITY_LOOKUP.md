## 0. 方針（一文）

> **市区町村の判定はビルド時に済ませ、配るのは「メッシュコード → 市区町村」の表だけにする。

## 1. 確定した要件

### R1 — データ源は e-Stat 国勢調査 小地域境界のみ

| | |
|---|---|
| ソース | `estat_boundary`（令和2年国勢調査 小地域・町丁・字等・JGD2011） |
| 状態 | **`config/sources.yml` に登録済。ライセンスゲート通過済**（2026-09-14、人による判断） |
| 再配布 | **可**。出典表示＋加工明示が条件 |

**N03 は使わない。** 行政区域そのものであり基準日も新しい（2025-01-01）が、測量法に基づく
国土地理院長承認（複製）R6JHf503 が併記されており、再配布の射程が未解決のため
（`N03_BOUNDARY_DESIGN.md` §8）。基盤地図情報・地球地図日本も同じ理由で除外。
OSM は ODbL のため除外。CODH 版は `POLICY.md` §2（発行元から直接取得）に反するため除外。

> ⚠️ **「行政区域」と名乗らないこと。** e-Stat の境界は調査区の境界であり、
> 発行元自身が「実際の町丁・字の境界と一致しない場合があります」と明記している。

**背景地図としての OSM タイルは利用してよい（2026-09-14 追記）。**
上の除外は**データ源としての取り込み**を指す。`GEO_EXPANSION_RESEARCH.md` §4 が OSM を ❌ と
したのは、ODbL の share-alike が派生データベースに及び、現在のライセンス構成を壊すからである。
**ラスタタイルを背景として表示するだけなら派生データベースを作らない**ので、この問題は生じない。
条件は `© OpenStreetMap contributors` の表示のみ。

- ⭕ Leaflet 等で `tile.openstreetmap.org` を背景表示する
- ❌ OSM の地物データを取り込んで対応表に混ぜる

> なお **Claude の Artifact では OSM タイルは表示できない**（CSP が外部画像を全面ブロックする）。
> タイルを使う地図アプリは GitHub Pages 側に置くこと。

### R2 — 判定に融合（dissolve）を使わない

小地域ポリゴンの属性 `PREF`(2桁) + `CITY`(3桁) を連結すると JIS 5桁市区町村コードになる。
**点in面してから属性を読む**だけでよく、融合は不要。

融合が要るのは**表示用の境界線を描くときだけ**で、それは加工にあたるが e-Stat 規約が
認めている（加工明示が条件）。

### R3 — ポリゴンの前処理

読み込み時に以下を必ず適用する。件数は実測値。

| 対象 | 判定条件 | 件数 | 扱い |
|---|---|---:|---|
| 町丁・字等 | `HCODE = 8101` | 231,668 | 採用 |
| 水面調査区 | `HCODE = 8154` | 351 | **除外**（港湾・漁港の水域。陸地ではない） |
| 抜け地 | `KIGO_D = 'D1'` | 7 | **除外**。他自治体の領域が食い込んだ「穴」。中の点を外側の市区町村と判定してはならない |
| 飛び地 | `KIGO_D = 'D'` | 323 | 採用（正規のポリゴン） |
| 島 | `KIGO_I = 'I'` | 3,787 | 採用 |
| 重複境域 | `KIGO_E` 非空 | 17,381 | 採用。**1町字＝1ポリゴンではない**。`AREA_MAX_F='M'` が最大面積 |

採用後のポリゴン **231,661件・頂点 30,799,102**（実測）。

`X_CODE` / `Y_CODE` は取り込まない。定義書に「属性情報については、JGD2000の値」とあり、
`.prj`（JGD2011）と測地系が食い違うため。

### R4 — メッシュは 3次（1km）

実測（正確版・2026-09-15 再計測。候補は現行市区町村＝lineage 読み替え後で数える）:

```
陸地セル   380,894
均一セル   312,132  (81.9%)   ← 1市区町村に収まる
混在セル    68,762  (18.1%)   ← 複数市区町村にまたがる
```

> 測定方法: 辺を 1/4 セル間隔で標本化してセルに割り当て、**加えて全セルで中心点の
> 点in面を行い、含むポリゴンをすべて候補に足す。** 外接矩形による粗い見積りでは 36.4% だった。
>
> ⚠️ **2026-09-14 版には誤りがあった。** 中心点の判定を「辺の通らないセル」にしか
> 行っていなかったため、県境（e-Stat は接合していない）で隣県ポリゴンの辺がわずかに
> 入り込んだセルでは、セル全体を覆う側の市区町村が落ちていた。51 セルが
> `contains`/`auto` で**面積 1% 未満の側の市区町村**を返していた。
>
> **独立検証（2026-09-15、shapely で全セルの交差面積を計算）:** 380,894 セル中
> 380,098 が候補集合まで一致。残りは既知の片側バイアスのみで、
> 取りこぼした候補の面積比は**最大 1.9%**（1% 以上は 6 件、10% 以上は 0 件）、
> 表に無い陸地セル 98 件はいずれも陸地がセルの 1% 未満。
> **角をかすめる候補を取りこぼしうるので混在率は floor。** 逆向き（無い候補を作る）は 0 件。

メッシュコードは**緯度経度からの算術のみ**で求まる（JIS X 0410）。データ参照は不要で、
ライセンス上の制約も断面のズレも一切ない。

### R5 — 分類は「候補集合＋理由」で返す

`bridge_station_municipality` と同じ形にする。**許容距離や最寄りへのスナップを使わない。**

| ヒット数 | `relation_type` | `verification_status` | 返すもの |
|---|---|---|---|
| 1 | `contains` | `auto` | 市区町村1件 |
| 複数 | `ambiguous` | `review_required` | **候補を全部**。1つに畳まない |
| 0 | `unresolved` | `review_required` | **空**。最寄りに寄せない |

**0件ヒットを最寄りポリゴンに寄せてはならない。** 0件の主因は県境で、e-Stat は都道府県境の
接合処理をしていない。隙間に落ちた点を寄せると県をまたいで誤る。

> 実測: 町字代表点 183,378点を全国結合で流したところ、0件は **72点（0.04%）**、
> 複数は 1点。`ESTAT_BOUNDARY_VERIFICATION.md` §7 の未解決事項 #1
> （全国結合時の県境の挙動）は、この測定で上限 0.04% と確定した。

### R6 — 混在セルは候補を返す（既定）

18.0% の混在セルは、**候補となる市区町村を全件返す**。ジオメトリはブラウザに配らない。

これは `POLICY.md` §4 の作法そのものである。

> Leaving data unresolved is acceptable. Inventing a wrong 1:1 mapping is a defect.

外接矩形版の測定では、混在セルの **87%（141,858件中 123,446件）が2市区町村のみ**だった。
正確版での内訳は未測定。

**将来の改善余地（いずれも本要件の範囲外）:**

- 4次メッシュ（500m）に細分すると混在率はおよそ半減する見込み（**推定**。未測定）。
  表は約4倍になる
- 混在セルに関わる**市区町村境の辺だけ**を配ればブラウザで確定できる。
  配布量は未測定

### R7 — 断面のズレを必ず経由させる

境界データは令和2年（2020年）国勢調査、市区町村は現在。**再編後の自治体では
現存しないコードが返る。**

実測で確認された不一致（jis_city_code）:

```
e-Stat のみ: 13199（東京都・市区町村名が空の集計行）, 22131〜22137（旧浜松7区）
jpac のみ  : 22138〜22140（新浜松3区）
```

- `overrides/municipality_lineage.yml` を**必ず経由**して現行コードに変換する
  （`tools/build_mesh_table.py` が `transitions` と `unlisted[].successors` を読む）
- **旧北区（22135 / lg 221350）は中央区と浜名区に分割されており、後継が一意でない。**
  1つに畳まず `ambiguous` として候補2件（221384 / 221392）を残す
- 1:1 の読み替え（中区・東区・西区・南区→中央区、浜北区 22136→浜名区、天竜区 22137→221406）は
  旧区の区域が新区に包含されるので、均一セルなら `auto` のまま。`mismatch_note` に読み替え元を残す
- 現行コードにも lineage にも無いコード（`13199` 等）の候補は捨てない。
  `mesh_mixed.bin` に `unknown_index`（65535）として載せる。捨てると、候補が1件に縮んで
  確定したように読めたり、セルごと消えて海と区別できなくなったりする
- 代表点 183,305件のうち市区町村が食い違ったのは **555件（0.30%）** で、大半がこれ

### R8 — 配布物の仕様

```
mesh_uniform.bin    均一かつ市区町村が特定できたセル 312,129件
                      「連続するメッシュコードで答えが同じ」区間（ラン）の列。すべて varint（LEB128）
                      ラン数、以後ランごとに：前のランの終わりからの差・長さ・市区町村インデックス
                    → 0.21 MB（固定長 <IH の初版は 1.87 MB）。ラン先頭で二分探索

mesh_mixed.bin      それ以外の陸地セル 68,765件（混在 68,762 ＋ 特定不能の均一 3）
                      同じくランの列。ランごとに：差・長さ・候補数・候補インデックス
                    → 0.28 MB（初版 0.63 MB）
                      候補 65535（municipality.json の unknown_index）は「特定できない候補」。
                      現状は 13199（東京都・市区町村名が空）の 8 セルのみ

3次コードの末尾2桁は 2次メッシュ内の行・列なので、00〜99 が1つの 2次メッシュ（約10km四方）になる。
市区町村はこの区間を丸ごと持つことが多く、ランにすると大きく縮む。
ページが最初に読む `mesh_data.js` は 3.49 MB → 0.79 MB。形式の仕様は `mesh.pack_lookup` の docstring

どちらにも無いセル = 陸地と判定されなかった（海・県境の隙間）。「特定できない」とは区別される

municipality.json   インデックス → lg_code / jis_city_code / 名称  （1,918件）

boundary.topojson   表示専用。小地域を市区町村で融合し簡素化したもの
                    ⚠️ 判定には使わない（簡素化で境界が動くため）
```

`Uint32Array` / `Uint16Array` として `fetch` + `ArrayBuffer` で読む。パースは不要。

> ⚠️ **表示用と判定用のポリゴンを混同しないこと。** 表示のために頂点を間引くと境界線が
> 数十〜数百メートル動き、境界付近の点はそれだけで誤判定する。判定はビルド時の
> 簡素化していないポリゴンで済ませ、その結果だけを配る。

### R9 — 下流に伝える制約

`DATA_LICENSE.md` の作法に従い、発行元が明記している注意事項5項目をそのまま同梱する。

1. 調査区の境界を基に作成しているため、実際の町丁・字の境界および名称と一致しない場合がある
2. 一つの市区町村内に同一の基本単位区・町丁字番号を持つ境域が複数存在する場合がある（重複フラグ付与）
3. 面積は境界データの図郭により算出したもので、国土地理院等の公式な面積と一致しない
4. 都道府県の境界線は接合処理を行っていないため、県境にずれが生じる場合がある
5. 他県の飛び地・水面調査区の境域情報が含まれる

出典表示と加工明示（`config/sources.yml` の `estat_boundary.attribution` に登録済）を
成果物に掲載する。

## 2. できないこと（明示する）

| 項目 | 理由 |
|---|---|
| **町字（住所）を返す** | e-Stat の小地域 231,668 に対し jpac の町字は 726,170。**約3.1倍の粒度差**があり、1つの面を複数の住所に展開することになる（`POLICY.md` §4 が欠陥と呼ぶ行為） |
| 番地・号・建物を返す | V1 スコープ外（`CLAUDE.md` §3） |
| 「行政区域」と称する | 調査区の境界であって行政界ではない |
| 境界データより高い精度 | 判定を高速化・厳密化しても、元の境界の正確さは超えない |

## 4.5 静的マップ（`site/`）

R1〜R9 を満たす実装。GitHub Pages でそのまま動く（サーバ処理なし・ビルド不要）。

| ファイル | 役割 |
|---|---|
| `site/index.html` / `style.css` | 画面。Leaflet 1.9.4（unpkg・SRI 固定）、背景は OSM タイル。アイコンは Material Icons（Apache-2.0）をインライン SVG で埋め込み、オフラインでも崩れない |
| `site/lookup.js` | 表引きの本体。メッシュコードの算術と `.bin` の読み取りだけ。DOM 非依存 |
| `site/app.js` | 地図・パネル・検索。メッシュの色分けは表からキャンバスに描く（ポリゴンは使わない） |
| `site/open-local.bat` / `serve.ps1` | ローカルで背景地図つきで開くためのランチャー。Windows 標準の PowerShell だけで `http://localhost` に配信する |

**画面の作法（一般的な Web 地図の操作系に合わせた）:**

| 操作 | 挙動 |
|---|---|
| 地図をクリック | 灰色のピン＋画面下のカード（市区町村・座標）。ダブルクリックは拡大のみ |
| カードをクリック | 左のサイドパネル（幅 408px、折りたたみ可）に地点の詳細。タイトルは度分秒の座標 |
| 緯度経度・メッシュコードを検索 | 赤いピン＋サイドパネル |
| 市区町村名を検索 | 1件ならその市区町村、複数なら候補一覧。範囲をメッシュ単位の赤い点線で示す |
| 住所を検索 | 先頭が一致する最長の市区町村に解決し、**残り（町字・番地）は扱わないと明示**する |
| 右クリック | 座標（クリックでコピー）・この場所について・拡大・色分け切替 |
| 左下のサムネイル / メニュー | メッシュの色分けの切替、このマップについて・出典 |

地点パネルの判定は4種（1つの市区町村／境界をまたぐ＝候補を全部／所属未定地／判定なし）を区別して
表示し、境界付近の地点を1つに畳んだり、判定なしを最寄りに寄せたりはしない（R5）。
| `site/data/mesh_data.js` | `tools/build_mesh_table.py --out site/data` の出力。R8 の2つの `.bin` と `municipality.json` を base64 で1本にまとめたもの（約 3.5 MB、gzip 配信時はそれ以下）。**これだけコミットする** |

- データ更新: `py -3.12 tools/build_mesh_table.py --out site/data`（`.bin` / `.json` / `.parquet` も
  出るが `.gitignore` 済み。ページは `mesh_data.js` しか読まない）
- **`fetch` ではなく `<script>` で読む理由**: ブラウザは `file://` からの `fetch` を CORS で塞ぐため、
  `index.html` をダブルクリックで開くとデータが読めない。`<script>` なら読める
- **`file://` では背景地図を出さない**: OSM はリファラの無いタイル要求を拒否し、全タイルが
  「Access blocked」になる。`file://` で開いた場合は背景なしで判定・色分けだけ動かし、パネルに理由を出す
- 公開: `.github/workflows/pages.yml`。`main` への push（`site/**` の変更時）でデプロイ。
  初回のみリポジトリの Settings → Pages → Source を「GitHub Actions」にする
- 検証: `tests/test_site_lookup.py` が Python の分類→`pack_lookup`→`lookup.js`（node）を通しで照合する。
  実データでは全 380,894 セル＋ランダム 50,000 点で不一致 0（2026-09-15）
- ローカル確認: `index.html` をダブルクリック（背景地図なし）、または `site/` で
  `py -3.12 -m http.server` → `http://127.0.0.1:8000/`（背景地図あり）

## 4.6 境界線と地点判定（`site/data/geo/`、POLICY.md §3.2）

メッシュ単位の答えでは「2県にまたがるメッシュ」の中の点を決められない。そこで地図には e-Stat の
境界そのものを載せ、**境界や海岸線が通るメッシュでは、クリックした地点そのものを点in面で判定する**。

| 出力 | 中身 | 用途 | 実測（2026-09-15） |
|---|---|---|---|
| `exact/PPUUQV.js` | 境界・海岸線が通る 3次セル 96,299 件に、各市区町村の陸地をセルで切り出した**非簡略**の形（断片 170,274） | 判定 | 4,488 ファイル・計 44.0 MB（gzip 31.5 MB）。1クリックで読むのは 2次メッシュ1つ分＝中央値 7 KB、最大 139 KB |
| `line/PPUU.js` | 輪郭を 0.0002°（約20m）で簡略化（県ごとに隣接辺を共有したまま）。水面調査区・抜け地を除いた跡の約1ha未満の穴は描かない | 表示（ズーム10以上） | 166 ファイル・計 5.2 MB（gzip 3.9 MB、中央値 15 KB） |
| `coarse/all.js` | 0.003°で簡略化し、画素未満の島・穴を落とした全国の輪郭 | 表示（ズーム9以下） | 0.65 MB |
| `units.js` | 境界単位 1,894（＝現行 `lg_code` の候補集合）・外接矩形・チャンク一覧 | 両方 | 0.19 MB |

- 生成: `py -3.12 tools/build_site_geo.py`（`pip install -e ".[geo]"` が必要。融合は `data/cache/` にキャッシュ）
- 座標は 1e-6°（約10cm）に量子化した zig-zag varint 差分。形式の仕様は `jp_address_crosswalk.build.geo_pack`
- **判定の手順**: メッシュコード → そのセルの `exact` 断片があれば点in面、無ければメッシュ表の答え
  （セル全体が1つの市区町村、または全体が海）。どの断片にも入らなければ「判定なし」（最寄りに寄せない）
- **検証**: 陸地セル・境界セル・全域（海を含む）から無作為に 35,000 点、境界セルの**セル辺から数cm以内**に
  10,000 点を取り、ページと同じ判定（node 上の `lookup.js` + `geo.js`）と、元の 231,661 ポリゴンに対する
  shapely の答え（pyogrio で別に読み込み、lineage も独立に読み替え）を比べた。**45,001 点で不一致 0**
  （地点判定 28,758 点・メッシュ判定 16,243 点）
- 検証で見つけて直した不具合: セル辺は 1/120°・1/80° の線で 1e-6° の格子に乗らないため、セルで切り出した断片の辺が
  最大 5e-7° 丸められ、セル辺ぎりぎりの点がどの断片にも入らず「判定なし」になった（35,000 点中 1 点・福井市）。
  断片をセルより約30cm 広く切り出して解消した（隣のセルの断片は判定に使わないので、候補が増えることはない）
- それでも決まらないもの: 県境で e-Stat の境界が重なる数メートル幅（両方を返す）と、旧浜松市北区
  （2024年の区界が2020年のデータに無いので、地点でも中央区・浜名区の2候補）

## 4.65 6次メッシュでの表示と軽量化（2026-09-16）

**メッシュは地図に重ねて表示し、6次メッシュ（約125m四方）を基本にする。**

- 6次メッシュ = 3次を縦横に8分割（JIS X 0410 の 1/2・1/4・1/8 地域メッシュ。各段 1=南西 2=南東
  3=北西 4=北東）。コードは 11桁（例 `53394611432`）。全国の表にすると約2,400万セルで配れないので、
  **表は作らず、表示中の範囲をブラウザで判定する**
- ズーム13以上: 境界の通る 3次セルだけを 64 の 6次セルに分け、各セルの中心と四隅を `exact` の形で
  点in面して色を決める（四隅に別の市区町村が現れたセルは「境界をまたぐ」灰色）。境界の通らない 3次セルは
  1色で塗る。結果は 3次セル単位でキャッシュ。ズーム12以下は 3次セルで塗る（6次は1画素未満）
- 地点パネルのメッシュコードとクリック時の枠は 6次。検索は 3次〜6次（8〜11桁）のコードを受け付ける
- 色分けは**表示用の近似**（6次セルの中心と四隅で見ている）。クリックした地点の判定は従来どおり地点そのもので行う

**軽量化（CPU プロファイルで決めたもの）:**

| 施策 | 根拠（プロファイル上の自己時間） |
|---|---|
| メッシュ表を「ラン」で持つ（`mesh_data.js` 3.49 MB → 0.79 MB） | 初期ロードで解析する量そのもの。復号＋展開は計 約7 ms |
| 境界線の索引を Map のバケットから型付き配列の外接矩形に、座標は z0 のメルカトル座標を前計算 | 索引構築 178 ms・点ごとの三角関数 53 ms が上位だった |
| 6次セルの塗りを色ごとにまとめ、同色の横並びを1矩形に | セルごとの fillStyle 切替 53 ms |
| 選択した市区町村の赤線を独立レイヤに | 選択のたびに全境界線・全メッシュを描き直していた |
| グリッドレイヤは地図が止まってから描く（`updateWhenIdle`）、保持タイルを減らす（`keepBuffer: 1`） | ズーム・パン中の無駄な再描画 |

同じ操作列（ロード→ズーム12〜15→パン4回→ズーム9→市区町村選択→地点クリック）のプロファイルで、
メインスレッドの処理時間は 1,623 ms → 1,259 ms（-22%）。

## 4.7 jpac との紐づけ

地図が返す市区町村は、すべて jpac と同じ **`lg_code`（6桁の全国地方公共団体コード）** で表す。
メッシュ表（`mesh_municipality`）も境界単位（`site/data/geo/units.js` の `units[].lg`）も同じ鍵なので、
jpac の `municipality` / `bridge_municipality_postal` / `bridge_municipality_telephone` などへは
`lg_code` の等値結合だけで繋がる。旧コード（e-Stat 側の JIS 5桁）は `boundary_jis_city_code` /
`units[].jis` に残し、`overrides/municipality_lineage.yml` 経由の読み替えであることを追えるようにしてある。

**段階1（実装済み・2026-09-16）:**
地点パネルと市区町村パネルから、その市区町村の**駅・郵便番号・市外局番**を表示する。
`tools/build_site_data.py` が `site/data/jpac_data.js`（1.27 MB）に書き出す:

| 中身 | 件数 | 備考 |
|---|---|---|
| 駅 | 9,046 グループ（うち市区町村に結び付くもの 8,988） | N02 のポリラインから求めた代表点つき。`build/spatial.py` の規則は駅→市区町村の結合と同じなので、地図のピンと `bridge_station_municipality` は食い違わない |
| 郵便番号 | 10,117 行 / 1,892 市区町村 | P3（「以下に掲載がない場合」等）は `postal_record_version` で実際の7桁に解決し、種別を残す |
| 市外局番 | 2,189 行 / 1,912 市区町村 | 番号区画経由。区画の一部だけを含む 479 行は発行元の但し書きをそのまま持つ |

駅は代表点を持つので3次メッシュごとにも索けるようにしてあり、地点パネルには
「このメッシュ内の駅」と「この市区町村の駅」を分けて出す。鍵はすべて `lg_code`。
前提だった出典表示はページに入れた（`POLICY.md` §3.2、`DATA_LICENSE.md` の文言のまま）。
