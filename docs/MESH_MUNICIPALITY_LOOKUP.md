## 0. 方針（一文）

> **市区町村の判定はビルド時に済ませ、配るのは「メッシュコード → 市区町村」の表だけにする。
> ポリゴンは読むだけで配らない。決まらない地点は決まらないと返す。**

## 1. 確定した要件

### R1 — データ源は e-Stat 国勢調査 小地域境界のみ

| | |
|---|---|
| ソース | `estat_boundary`（令和2年国勢調査 小地域・町丁・字等・JGD2011） |
| 状態 | **`config/sources.yml` に登録済。ライセンスゲート通過済**（2026-09-14、人による判断） |
| 再配布 | **可**。出典表示＋加工明示が条件 |

**N03 は使わない。** 行政区域そのものであり基準日も新しい（2025-01-01）が、測量法に基づく
国土地理院長承認（複製）R6JHf503 が併記されており、再配布の射程が未解決のため
（`N03_BOUNDARY_DESIGN.md` §8）。基盤地図情報・地球地図日本も同じ理由で除外。
OSM は ODbL のため除外。CODH 版は `POLICY.md` §2（発行元から直接取得）に反するため除外。

> ⚠️ **「行政区域」と名乗らないこと。** e-Stat の境界は調査区の境界であり、
> 発行元自身が「実際の町丁・字の境界と一致しない場合があります」と明記している。

**背景地図としての OSM タイルは利用してよい（2026-09-14 追記）。**
上の除外は**データ源としての取り込み**を指す。`GEO_EXPANSION_RESEARCH.md` §4 が OSM を ❌ と
したのは、ODbL の share-alike が派生データベースに及び、現在のライセンス構成を壊すからである。
**ラスタタイルを背景として表示するだけなら派生データベースを作らない**ので、この問題は生じない。
条件は `© OpenStreetMap contributors` の表示のみ。

- ⭕ Leaflet 等で `tile.openstreetmap.org` を背景表示する
- ❌ OSM の地物データを取り込んで対応表に混ぜる

> なお **Claude の Artifact では OSM タイルは表示できない**（CSP が外部画像を全面ブロックする）。
> タイルを使う地図アプリは GitHub Pages 側に置くこと。

### R2 — 判定に融合（dissolve）を使わない

小地域ポリゴンの属性 `PREF`(2桁) + `CITY`(3桁) を連結すると JIS 5桁市区町村コードになる。
**点in面してから属性を読む**だけでよく、融合は不要。

融合が要るのは**表示用の境界線を描くときだけ**で、それは加工にあたるが e-Stat 規約が
認めている（加工明示が条件）。

### R3 — ポリゴンの前処理

読み込み時に以下を必ず適用する。件数は実測値。

| 対象 | 判定条件 | 件数 | 扱い |
|---|---|---:|---|
| 町丁・字等 | `HCODE = 8101` | 231,668 | 採用 |
| 水面調査区 | `HCODE = 8154` | 351 | **除外**（港湾・漁港の水域。陸地ではない） |
| 抜け地 | `KIGO_D = 'D1'` | 7 | **除外**。他自治体の領域が食い込んだ「穴」。中の点を外側の市区町村と判定してはならない |
| 飛び地 | `KIGO_D = 'D'` | 323 | 採用（正規のポリゴン） |
| 島 | `KIGO_I = 'I'` | 3,787 | 採用 |
| 重複境域 | `KIGO_E` 非空 | 17,381 | 採用。**1町字＝1ポリゴンではない**。`AREA_MAX_F='M'` が最大面積 |

採用後のポリゴン **231,661件・頂点 30,799,102**（実測）。

`X_CODE` / `Y_CODE` は取り込まない。定義書に「属性情報については、JGD2000の値」とあり、
`.prj`（JGD2011）と測地系が食い違うため。

### R4 — メッシュは 3次（1km）

実測（正確版・2026-09-14）:

```
陸地セル   380,894
均一セル   312,366  (82.0%)   ← 1市区町村に収まる
混在セル    68,528  (18.0%)   ← 複数市区町村にまたがる
```

> 測定方法: 辺を 1/4 セル間隔で標本化してセルに割り当て、辺の通らないセルは
> 中心点の点in面で陸地判定。**角をかすめるセルを取りこぼしうるので混在率は floor。**
> 外接矩形による粗い見積りでは 36.4% だった。

メッシュコードは**緯度経度からの算術のみ**で求まる（JIS X 0410）。データ参照は不要で、
ライセンス上の制約も断面のズレも一切ない。

### R5 — 分類は「候補集合＋理由」で返す

`bridge_station_municipality` と同じ形にする。**許容距離や最寄りへのスナップを使わない。**

| ヒット数 | `relation_type` | `verification_status` | 返すもの |
|---|---|---|---|
| 1 | `contains` | `auto` | 市区町村1件 |
| 複数 | `ambiguous` | `review_required` | **候補を全部**。1つに畳まない |
| 0 | `unresolved` | `review_required` | **空**。最寄りに寄せない |

**0件ヒットを最寄りポリゴンに寄せてはならない。** 0件の主因は県境で、e-Stat は都道府県境の
接合処理をしていない。隙間に落ちた点を寄せると県をまたいで誤る。

> 実測: 町字代表点 183,378点を全国結合で流したところ、0件は **72点（0.04%）**、
> 複数は 1点。`ESTAT_BOUNDARY_VERIFICATION.md` §7 の未解決事項 #1
> （全国結合時の県境の挙動）は、この測定で上限 0.04% と確定した。

### R6 — 混在セルは候補を返す（既定）

18.0% の混在セルは、**候補となる市区町村を全件返す**。ジオメトリはブラウザに配らない。

これは `POLICY.md` §4 の作法そのものである。

> Leaving data unresolved is acceptable. Inventing a wrong 1:1 mapping is a defect.

外接矩形版の測定では、混在セルの **87%（141,858件中 123,446件）が2市区町村のみ**だった。
正確版での内訳は未測定。

**将来の改善余地（いずれも本要件の範囲外）:**

- 4次メッシュ（500m）に細分すると混在率はおよそ半減する見込み（**推定**。未測定）。
  表は約4倍になる
- 混在セルに関わる**市区町村境の辺だけ**を配ればブラウザで確定できる。
  配布量は未測定

### R7 — 断面のズレを必ず経由させる

境界データは令和2年（2020年）国勢調査、市区町村は現在。**再編後の自治体では
現存しないコードが返る。**

実測で確認された不一致（jis_city_code）:

```
e-Stat のみ: 13199（東京都・市区町村名が空の集計行）, 22131〜22137（旧浜松7区）
jpac のみ  : 22138〜22140（新浜松3区）
```

- `overrides/municipality_lineage.yml` を**必ず経由**して現行コードに変換する
- **旧北区（22135）は中央区と浜名区に分割されており、後継が一意でない。**
  変換せず `ambiguous` として候補2件を残す
- 代表点 183,305件のうち市区町村が食い違ったのは **555件（0.30%）** で、大半がこれ

### R8 — 配布物の仕様

```
mesh_uniform.bin    均一セル 312,366件
                      メッシュコード(3次・8桁) uint32   4 bytes
                      市区町村インデックス      uint16   2 bytes
                    → 約 1.9 MB。メッシュコード昇順、二分探索

mesh_mixed.bin      混在セル 68,528件 → 候補市区町村インデックスの配列

municipality.json   インデックス → lg_code / jis_city_code / 名称  （1,918件）

boundary.topojson   表示専用。小地域を市区町村で融合し簡素化したもの
                    ⚠️ 判定には使わない（簡素化で境界が動くため）
```

`Uint32Array` / `Uint16Array` として `fetch` + `ArrayBuffer` で読む。パースは不要。

> ⚠️ **表示用と判定用のポリゴンを混同しないこと。** 表示のために頂点を間引くと境界線が
> 数十〜数百メートル動き、境界付近の点はそれだけで誤判定する。判定はビルド時の
> 簡素化していないポリゴンで済ませ、その結果だけを配る。

### R9 — 下流に伝える制約

`DATA_LICENSE.md` の作法に従い、発行元が明記している注意事項5項目をそのまま同梱する。

1. 調査区の境界を基に作成しているため、実際の町丁・字の境界および名称と一致しない場合がある
2. 一つの市区町村内に同一の基本単位区・町丁字番号を持つ境域が複数存在する場合がある（重複フラグ付与）
3. 面積は境界データの図郭により算出したもので、国土地理院等の公式な面積と一致しない
4. 都道府県の境界線は接合処理を行っていないため、県境にずれが生じる場合がある
5. 他県の飛び地・水面調査区の境域情報が含まれる

出典表示と加工明示（`config/sources.yml` の `estat_boundary.attribution` に登録済）を
成果物に掲載する。

## 2. できないこと（明示する）

| 項目 | 理由 |
|---|---|
| **町字（住所）を返す** | e-Stat の小地域 231,668 に対し jpac の町字は 726,170。**約3.1倍の粒度差**があり、1つの面を複数の住所に展開することになる（`POLICY.md` §4 が欠陥と呼ぶ行為） |
| 番地・号・建物を返す | V1 スコープ外（`CLAUDE.md` §3） |
| 「行政区域」と称する | 調査区の境界であって行政界ではない |
| 境界データより高い精度 | 判定を高速化・厳密化しても、元の境界の正確さは超えない |

## 3. 手続き上やるべきこと

### P1 — `POLICY.md` のスコープ拡張

現行 §3 は mesh codes をスコープ外と明記している。駅を追加したときと同じく、
**§3.1 に相当するスコープ拡張の記録**を残す。ライセンス問題は無いので手続きのみ。

### P2 — ポリゴン非配布方針との整理

`POLICY.md` §3.1 は「ポリゴンはビルド時に読むだけ。成果物には入れない」と定めている。
**本要件はこれを守る**（配るのは表であってポリゴンではない）が、
表示用 TopoJSON を配る場合は方針の改訂が要る。e-Stat のライセンス上は可能なので、
これも手続きの問題である。

### P3 — 別成果物として切り出す

本件は jpac のリリース成果物（対応表）とは別種のプロダクトである。
`GEO_EXPANSION_RESEARCH.md` §8 の (d) が「別リポジトリ・空間結合済みの兄弟成果物」を
推奨しているのと同じ整理に従う。
