# N03_BOUNDARY_DESIGN.md — 国土数値情報 N03 行政区域を jpac に紐づける

市区町村ポリゴン（国土数値情報 **N03 行政区域**）を jpac に接続するための設計。

- 設計日: **2026-09-05**
- 前提調査: [`GEO_EXPANSION_RESEARCH.md`](GEO_EXPANSION_RESEARCH.md) §5（レイヤ別ライセンス）・§10（N02）
- 規律: [`POLICY.md`](POLICY.md) / [`LICENSE_POLICY.md`](LICENSE_POLICY.md) / [`../DATA_LICENSE.md`](../DATA_LICENSE.md)

> **この文書は設計であって、実装の許可ではない。** §8 のライセンスゲートを人手で
> 通すまで、N03 は `config/sources.yml` に入らない。

---

## 0. 結論（先に3つ）

1. **N03 と jpac は空間演算なしで繋がる。** N03 は属性に `N03_007`
   全国地方公共団体コード（5桁）を持つので、jpac の `jis_city_code` との
   **キー結合**で足りる。この接続に推定は一切入らない。
2. **したがって成果物は「対応表」ではなく「ポリゴンの取り付け口＋突合レポート」。**
   コード同士が 1:1 で確定する以上、confidence を持つ bridge 表を作っても情報量がゼロ。
   価値があるのは、**両者の市区町村集合がどこで食い違うか**を根拠付きで記録する側。
3. **⚠️ N03 のポリゴンは、そのままでは再配布できない可能性が高い。**
   利用許諾条件は「オープンデータ（CC_BY_4.0）」だが、**同じページに測量法に基づく
   国土地理院長承認番号と「複製には国土地理院の長の承認を得なければなりません」が
   併記されている**（§8）。これは `GEO_EXPANSION_RESEARCH.md` §6.4 が 基盤地図情報 を
   ❌ にしたのと同じ根拠である。**この設計がジオメトリを同梱しない（§7 案 A）のは、
   サイズの都合ではなくライセンスの要請**として読むこと。

## 2. 接続方式 — キー結合。実測で裏を取った

`N03_007` は 5 桁の全国地方公共団体コード。jpac 側の受け口は `municipality.jis_city_code`。

`dist/jp_address_crosswalk.sqlite`（v1.0.0）で実測（2026-09-05）:

| 検査 | 結果 |
|---|---|
| `municipality` 行数 | **1,918** |
| `jis_city_code` の異なり数 | **1,918**（＝重複なし。ファンアウトしない） |
| `jis_city_code` が NULL の行 | **0** |
| 桁数 | 全行 **5 桁** |
| `substr(lg_code,1,5) <> jis_city_code` の行 | **0**（README.md:146 の主張は全行で成立） |

> **`jis_city_code` は事実上の一意キーとして使ってよい。** ただしスキーマ上の
> PRIMARY KEY は `lg_code` なので、結合後は `lg_code` に持ち替えること。
> jpac の他の表はすべて `lg_code` を軸にしている。

```
N03_007 (5桁)  ──キー結合──>  municipality.jis_city_code  ──>  lg_code
                                                                 ├─> bridge_municipality_postal    （郵便番号）
                                                                 ├─> bridge_municipality_telephone （番号区画）
                                                                 └─> address / bridge_address_mlit （町字・国交省コード）
```

**`lg_code` は `013100` のように先頭がゼロになる**（README.md:733）。N03 側の
`N03_007` も同様に `01100` である。**両側とも文字列で読むこと。**
Shapefile の DBF を数値型として読むライブラリがあるので、読み込み時に明示的に
文字列指定し、5 桁ゼロ埋めを検証する。

## 3. スキーマ — ポリゴンは「関係」ではなく「属性」

bridge 表を作らない。`bridge_municipality_postal` / `_telephone` が `lg_code` を
**別の ID 体系の識別子**に対応づけるのに対し、N03 が与えるのは市区町村そのものの
**性質**（形）だからである。confidence 1.0・relation_type exact で埋まるだけの
bridge 表は、何も記録していないのと同じになる。

### 3.1 `municipality_boundary`

```sql
CREATE TABLE "municipality_boundary" (
  "boundary_id"          TEXT PRIMARY KEY,
  "lg_code"              TEXT,          -- jpac 側のキー（結合後に持ち替え）
  "jis_city_code"        TEXT,          -- N03_007 の生値（5桁・文字列）
  "n03_edition"          TEXT,          -- '2025'
  "n03_reference_date"   TEXT,          -- '2025-01-01'
  "part_index"           INTEGER,       -- 飛地・島嶼。0 起点
  "part_count"           INTEGER,
  "geometry"             BLOB,          -- WKB。§7 の判断次第では NULL のまま出す
  "geometry_crs"         TEXT,          -- 'EPSG:6668' (JGD2011 経緯度)
  "area_sqm"             REAL,          -- 面積は測地系依存。算出方法を derivation に書く
  "centroid_lat"         REAL,
  "centroid_lon"         REAL,
  "boundary_status"      TEXT,          -- 'determined' | 'provisional' | 'unassigned'
  "n03_pref_name_raw"    TEXT,          -- N03_001
  "n03_branch_name_raw"  TEXT,          -- N03_002 北海道の振興局
  "n03_county_name_raw"  TEXT,          -- N03_003
  "n03_city_name_raw"    TEXT,          -- N03_004
  "n03_ward_name_raw"    TEXT,          -- N03_005 政令市の区名（2025年版のみ）
  "reconcile_status"     TEXT,          -- §5 の5分類
  "reconcile_note"       TEXT,
  "derivation"           TEXT,
  "source_snapshot_id"   TEXT,
  "created_at"           TEXT,
  "updated_at"           TEXT,
  CHECK (boundary_status IN ('determined','provisional','unassigned')),
  CHECK (reconcile_status IN ('matched','designated_city_parent','jpac_only',
                              'n03_only','unassigned_area')),
  CHECK (part_index >= 0),
  CHECK (part_index < part_count)
);
CREATE INDEX idx_mb_lg   ON municipality_boundary(lg_code);
CREATE INDEX idx_mb_jis  ON municipality_boundary(jis_city_code);
CREATE INDEX idx_mb_rec  ON municipality_boundary(reconcile_status);
```

### 3.2 飛地は dissolve しない

1 市区町村が複数ポリゴンを持つ（島嶼・飛地）。これを 1 つの MULTIPOLYGON に
融合するのは **加工**であり、`DATA_LICENSE.md` の「加工したなら加工したと言う」に
掛かる。**発行元の形のまま `part_index` で持つ**のが既定。融合が必要なら利用側で
やればよく、その方が何をしたかが利用者から見える。

### 3.3 `part_count` の意味に注意

`part_count` は「N03 のこの版において、この `N03_007` が持つポリゴン数」であって
「この市区町村の島の数」ではない。**版が変われば変わる。** 列コメントに書く。

## 4. 政令指定都市の親 — jpac 側は実測 20件。N03 側の行の持ち方は**未確認**

### 4.1 未解決の前提 — `N03_007` は区コードか、市コードか

詳細ページの `N03_007` の定義は逐語でこうである（2026-09-05）:

> 「JIS X 0401で定められている都道府県コード2桁と、JIS X 0402で定められている
> 市区町村コード3桁から構成される5桁の数字で表現されたコード」

**政令指定都市についてこの定義は何も言っていない。** JIS X 0402 は区にもコードを
与えている（例 `14101` 横浜市鶴見区）ので区コードが入る読みが自然だが、
`N03_005` に区名という**別の属性が用意されている**以上、
`N03_007` は市コード（`14100`）で区は `N03_005` でのみ区別する、という読みも成り立つ。
**ページからは決められない。**

| 読み | N03 側の行 | 帰結 |
|---|---|---|
| **W（区コード説）** | `14101` 鶴見区… | jpac の**区 171 件**にポリゴンが付き、**親 20 件**は付かない |
| **C（市コード説）** | `14100` 横浜市（区ごとに複数行、コードは同じ） | jpac の**親 20 件**にポリゴンが付き、**区 171 件**は付かない |

> **どちらかを仮定してコードを書かないこと。** §10 の #3 で神奈川県を 1 県だけ取得し、
> `N03_007` の実値を見て決める。両方の読みに対応する分岐を先に書くのは過剰設計なので、
> **測ってから片方を書く**。

以下 §4.2 は読み W を前提に書いてあるが、C だった場合は
`designated_city_parent` と「区側が空になる」分類が入れ替わるだけで、構造は同じである。

### 4.2 jpac 側の実測

一方 jpac は **親市と区の両方**を持つ。実測（同 SQLite、2026-09-05）:

| 検査 | 結果 |
|---|---|
| `municipality_version` の現行行で `ward` が非 NULL | **171 行**（＝区） |
| その親市の異なり数 | **20**（札幌・仙台・さいたま・千葉・横浜・川崎・相模原・新潟・静岡・浜松・名古屋・京都・大阪・堺・神戸・岡山・広島・北九州・福岡・熊本） |
| `13100`（東京都特別区部）の集約行 | **無し**（特別区は区ごとに独立。親問題は起きない） |

> **したがって、親政令市 20 件は N03 側に対応ポリゴンが存在しないのが正しい。**
> これを不一致として報告し続けると、本物の不一致 15 件程度が 35 件のノイズに
> 埋もれる。`reconcile_status = 'designated_city_parent'` として**最初から別分類**にする。

親の境界が要る場合は、区ポリゴンの和で導出できる。ただしそれは**導出物**なので
`derivation` に明示し、N03 が配ったポリゴンと同じ表に混ぜない。既定では作らない。

**注意**: 「コードが `00` で終わる＝政令市の親」ではない。実測では `00` 終わりが
17 件あり、そのうち `01400` 倶知安町 と `01700` 蘂取村 は普通の町村である。逆に
川崎市 `14130`・相模原市 `14150`・浜松市 `22130`・堺市 `27140` は `00` で終わらない親である。
**判定は「N03 側に区として子コードが存在するか」で行う**こと。コードの見た目で判定しない。

## 5. 突合ロジック — 5分類。不一致を消さない

両側の市区町村コード集合を突き合わせ、**全件をいずれかに分類する**。
`POLICY.md` §5（無マッチ行を消さない）と §4（曖昧は曖昧のまま）をそのまま適用する。

| `reconcile_status` | 条件 | 扱い |
|---|---|---|
| `matched` | 両側にコードが存在 | 正常。ポリゴンを取り付ける |
| `designated_city_parent` | jpac にあり、N03 には区としてのみ存在（§4） | **正常な差**。ポリゴンは付かない |
| `jpac_only` | jpac にあり N03 に無い（上記以外） | **要調査。** 廃置分合の疑い。`overrides/municipality_lineage.yml` を引く |
| `n03_only` | N03 にあり jpac に無い | **要調査。** N03 の方が新しい／古い可能性 |
| `unassigned_area` | N03 側に `N03_007` が空、または所属未定地 | ポリゴンは保持、`lg_code` は NULL |

### 5.1 `jpac_only` / `n03_only` は年度差として説明を試みる

N03 2025年版は基準日 2025-01-01、jpac は 2026 年の ABR。**この 1 年強の差に
廃置分合があれば、必ず両方向に出る。** 片方向だけ出た場合は年度差では説明できないので、
その旨を `reconcile_note` に書いて残す（勝手に潰さない）。

jpac は既に `overrides/municipality_lineage.yml` を持っている（README.md:438 の I3 で使用）。
**同じ登記簿を N03 の突合でも引く。** 新しく別の履歴表を作らないこと。

### 5.2 出力

`dist/QUALITY_REPORT.md` に節を足すのではなく、**`dist/N03_RECONCILE.md` として独立**させる。
理由は、これが jpac 本体の品質ではなく **2つのデータセット間の版ズレ**の記録だからで、
本体の品質指標に混ぜると「jpac の欠陥」に見えてしまう。

## 6. 境界未定・所属未定地

N03 の詳細ページ（2026-09-05 取得）が明記している:

> 一部の市区町村において境界が未確定の地域があります（暫定的な境界）。
> **東京都千代田区・中央区・港区**の境界は補正が行われた。暫定境界の一覧は別掲。

- `boundary_status = 'provisional'` を立て、**別掲の暫定境界一覧を取り込んで根拠にする**
  （一覧そのものの取得可否は未確認。ここは実装時に確認する）
- **千代田・中央・港が入っているのは重い。** ここは jpac の需要が最も高い区域である
- **所属未定地**（`N03_007` が空のレコード）が 2025年版に何件あるかは**未実測**。
  実装の最初のステップで数えること。0 件かもしれないし、そうでないかもしれない。
  数えずに「無いものとして」書くコードにしない

> ⚠️ 「境界が暫定である」ことは、**この設計の下流に必ず伝える**。
> `boundary_status` を持つだけでなく、`NOTICE.md` に一文を足す。
> 暫定境界を確定境界のように扱わせるのは、`DATA_LICENSE.md` が代表点について
> 「建物位置ではない」と書いたのと同じ種類の責任である。

## 7. サイズと配布 — ポリゴンは既定で同梱しない

N03 のファイルサイズは、詳細ページによると **全国版で約 230MB〜727MB**（年次による）、
**都道府県別は 0.8〜54MB**。

`config/sources.yml` の `http` 設定は
`max_download_bytes: 536870912`（512MiB）/ `max_uncompressed_bytes: 2147483648`（2GiB）。

> **全国版 GML は両方の上限に触れうる。** 取得は**都道府県別 Shapefile を 47 回**に分ける。
> GML（JPGIS2014 XML）は展開後が大きく、2GiB 上限に当たる可能性がある。

配布方針:

| 案 | 内容 | 判定 |
|---|---|---|
| **A（採用）** | `municipality_boundary` は出すが `geometry` は NULL。突合結果・`part_count`・代表点・`boundary_status` のみ配る | ⭕ リリースサイズが変わらない。利用者は N03 を自分で落として `lg_code` で繋げる |
| B | ジオメトリを簡略化して同梱 | ❌ 簡略化は加工。しかも「どれだけずらしたか」を利用者が検証できない |
| C | ジオメトリを原形のまま同梱 | ❌ **§8 の国土地理院長承認が未解決の間は不可。** サイズ以前にライセンスで止まる |

**A を採用する。** §8 の通り N03 には「複製には国土地理院の長の承認を得なければ
なりません」が併記されており、**ジオメトリの再配布はこの承認の対象になりうる**。
案 C は、承認要否が人手のゲート（§8）で決着し、必要なら承認を取ってからでなければ
選べない。

A であれば、jpac は**空間データを配るプロジェクトにならずに済む**——
空間処理はビルド時の 1 工程に閉じ、出荷物は今まで通り表である。
そして**この構成なら承認問題そのものを回避できる**: 代表点・面積・突合結果は
ポリゴンの複製ではないので、`geometry` を持たない限り複製の議論に入らない。

> ただし「代表点と面積はポリゴンの複製にあたらない」は**本設計の判断であって、
> 発行元の言明ではない**。§8 のゲートで人が確認する項目に含めること。

## 8. ライセンス — `sources.yml` にはまだ入れない

### 8.0 ⚠️ 素の CC BY 4.0 ではない — 測量法の承認要件が併記されている

詳細ページの利用許諾条件欄は、**逐語でこう書かれている**（2026-09-05 取得）:

> 「オープンデータ（CC_BY_4.0）
> ※本データを二次利用する場合には、**国土地理院に申請等必要な場合があります。**」

さらに同ページ本文に:

> 「測量法に基づく国土地理院長承認（複製）**R 6JHf 503**」
> 「**本製品を複製する場合には、国土地理院の長の承認を得なければなりません。**」

**これは `GEO_EXPANSION_RESEARCH.md` §5.4 が N03 を「⭕ 素の CC BY 4.0」に分類した
根拠（一覧ページの表記のみ）を、詳細ページが覆したケースである。**
同 §5.4 は自分で「一覧ページの表記をそのまま結論にしてはいけない」と警告しており、
その警告が的中した形になる。

構造としては、`GEO_EXPANSION_RESEARCH.md` §6.4 が 基盤地図情報 を ❌ にした
測量法 §29/§30 の問題と**同じもの**である。N03 のポリゴンは国土地理院の
基本測量成果を複製して作られており、その承認番号がページに書かれている。

したがって現時点の判定は **`clear` ではなく `conditional`**:

| 対象 | 判定 |
|---|---|
| N03 を**利用**して突合表を作る | ⭕ CC BY 4.0 の範囲。出典表示で足りる見込み |
| N03 の**ポリゴンを再配布**する | 🔶 **国土地理院長の承認が要る可能性が高い。未解決** |
| 代表点・面積・件数など、ポリゴンから導いた数値を配る | 🔶 「複製」に当たるかの判断が要る。**§7 の注記の通り、これは本設計の判断であって発行元の言明ではない** |

**§7 で案 A（ジオメトリ非同梱）を採るのは、この未解決を踏み越えないためである。**

### 8.1 ゲートの手順

`GEO_EXPANSION_RESEARCH.md` §5.3 の判定ルールに掛けると、素の
「オープンデータ（CC BY 4.0）」であれば新規約（PDL 1.0）側だが、
上記の通り**素ではない**。

**これは下調べであって、ゲートを通ったことにはならない。**
`LICENSE_POLICY.md` §4 は明示している——

> Clearing the gate requires a human to read the new terms, update this file and
> `config/sources.yml`, and commit the new hash with a rationale.
> No automatic acceptance path exists.

したがって手順は:

1. N03 は **`config/candidate_sources.yml`** に置く（本コミットで実施）
2. 人が N03 詳細ページと `agreement.html` を**逐語で読む**
3. **国土地理院承認（R 6JHf 503）の射程を決着させる。**
   「二次利用に申請が必要な場合」とは何か、突合表の配布・代表点の配布が
   それに当たるか。**ページの読解だけで決まらなければ、国土地理院への照会が要る。**
   `GEO_EXPANSION_RESEARCH.md` §6.4 で 基盤地図情報 を退けた判断との整合も取る
4. `text_sha256` / `text_sha256_decoded` を計算し、**理由付きで commit**
5. そこで初めて `config/sources.yml` に `mlit_ksj_n03` として追加

**#3 が未決着のうちは、案 A（ジオメトリ非同梱）でも配布に進まない。**
利用（ビルド時に読む）と配布は別の判断である。

### 8.2 既存の `mlit` エントリに相乗りさせないこと

`config/sources.yml` の `mlit` は **位置参照情報**のエントリで、その
`review_2026_08_24` は「位置参照情報は §1.3 の対象外」と明記している。
**N03 は 国土数値情報 であり、§1.3 の判定を個別に受ける別物**である。
同じ省庁だからと 1 エントリにまとめるのは、`DATA_LICENSE.md` が禁じた
「異なる条件を 1 つに丸める」そのものになる。**`mlit_ksj_n03` として独立させる。**

### 8.3 出典表示

N03 は加工の有無で文言が変わる。案 A（ジオメトリ非同梱）でも、
**突合結果は N03 を加工して作った派生物**なので処理済み側の文言が要る。
実際の文言は発行元の 出典記載例 を逐語で確認してから `NOTICE.md` に入れる。

加えて、**国土地理院長承認番号（R 6JHf 503）を表示する義務があるか**を §8.1 #3 で
確認する。承認番号の表示は測量法系の成果で通例求められるもので、
CC BY 4.0 の出典表示とは別の要件である。

## 9. POLICY の改定が要る点

`POLICY.md` §3 の V1 スコープ外リストは
「POI, facilities, corporations…, **stations, roads**, …, census areas」を挙げている。
N03 行政区域はこの列挙に直接は無いが、**§3 が想定していないクラスのデータ**（幾何ペイロード）である。

必要な改定:

- §3 に「V2 で許可する取得元」として 国土数値情報 N03 を明記する
- §2（V1 granularity は町字、それ以下は無し）に対し、**N03 は町字より上位**なので
  粒度の禁止には触れないことを確認して書く
- 「ジオメトリを持つが既定では配らない」というクラスを `POLICY.md` に定義する

**この改定を先に通すこと。** 設計だけ先に進めて後から POLICY を追認させるのは、
このプロジェクトが避けてきたやり方である。

### #3 に神奈川県を選ぶ理由

この設計で最も危ういのは §4.1（`N03_007` の読み）である。**東京都には
政令指定都市が無いので、東京都で試しても §4.1 は一切検証できない。**
神奈川県は 横浜・川崎・相模原 の 3 政令市を含み、しかも
**川崎 `14130`・相模原 `14150` は `00` で終わらない**ので、§4 が警告した
「コードの見た目で親を判定する」罠も同時に踏み抜ける。

東京都は #5（千代田・中央・港の暫定境界）の確認用として別に使う。

### #7 の当たり判定

`designated_city_parent` の件数は、**§4.1 のどちらの読みだったかを示す測定値**である。
20 でなければ実装が壊れている、とは言えない:

| 観測 | 意味 |
|---|---|
| `designated_city_parent` = **20** | 読み **W**（区コード説）。区 171 件にポリゴンが付く |
| 親 20 件にポリゴンが付き、区 171 件が空 | 読み **C**（市コード説）。分類名を付け替える（`designated_city_ward` 等） |
| どちらでもない | **§4.1 の 2 つの読み以外の構造。設計を書き直す** |

#4 で読みを確定させてから #7 に入るので、通常はここで驚きは起きない。
起きたら #4 の判定が誤っている。

## 11. この設計が意図的にやらないこと

| やらないこと | 理由 |

| 町字にポリゴンを与える | N03 は市区町村止まり。町字ポリゴン問題は `GEO_EXPANSION_RESEARCH.md` §3 のまま未解決 |
| 市区町村の統計を町字に按分する | `POLICY.md` §4「市区町村レベルの言明を町字に展開しない」 |

| 名前（`N03_004`）で突合する | コードで確定するのに文字列一致を持ち込む理由がない。名前は `*_raw` として保持するのみ |
